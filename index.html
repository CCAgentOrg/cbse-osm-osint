CBSE OSM Vendor Leaked Its Own Attack Code to GitHub

Internal QA automation from Coempt EduTeck reveals an evaluation portal with no real OTP, predictable answer-sheet IDs, and a password-change flow that doesn't verify the old password.

30 May 2026 • OSINT Investigation • Technical Annexure • API Surface Analysis

⚠ Correction & Scope Note

The Andhra Pradesh SBTET source code (viswanthp/AP_SBTET_AUDIT) found during this investigation is a separate codebase for a different board, built on the same OnMark platform by the same vendor (Coempt EduTeck). While architecturally similar, it is not the CBSE evaluation system. This article covers only CBSE-specific evidence unless explicitly noted otherwise.

The Attack Surface Is Shared

The OnMark evaluation platform — built and operated by Coempt EduTeck — is not unique to CBSE. SSL certificate records reveal over 30 board subdomains on onmark.co.in, each an identical instance of the same ASP.NET application serving different state boards and universities across India.

At least two instances remain live and responding as of May 2026:

SubdomainBoardStatusServer
cbseosm.onmark.co.inCBSE (Central Board)503 — MaintenanceMicrosoft IIS/10.0

Both run the same Angular SPA at /cbseevalweb/ and share the same OnMarkWinWebAPI controller surface. Any vulnerability found in one instance is likely present in all of them.

What We Found

Through passive OSINT — examining a 1.7 MB JavaScript bundle recovered from the Internet Archive's Wayback Machine, and cross-referencing it against Coempt's own Selenium automation code left on GitHub — we identified three high-confidence API-level vulnerabilities in the CBSE evaluation portal.

None of these were reported in the earlier responsible disclosure by security researcher Nisarga Adhikary, who focused on authentication bypass and route guard issues.

Vulnerability 1: Answer-Sheet PDFs Downloadable via Sequential IDs

The portal generates a total_marks_id for each evaluated answer sheet and serves the final marked PDF at a predictable URL:

apiurl + "Download/finalpdf/" + total_marks_id + ".pdf"

The bundle contains a hardcoded sample: total_marks_id: "93836". If this is an auto-incrementing database integer — which the five-digit number strongly suggests — any authenticated evaluator could enumerate IDs (93835, 93837, …) and download other evaluators' completed, annotated answer sheets. This is a textbook IDOR (Insecure Direct Object Reference).

The PDF opens in a new browser window at 800×600 with scrolling, meaning the system was designed for evaluators to review each other's marked scripts.

Vulnerability 2: Password Change Requires No Old Password

The ChangePassword endpoint accepts a payload of only two fields:

{ValuatorID: user_id, pin_NewPassword: new_password}

There is no old_password field — neither in the client-side form nor in the API payload. The HTML form only shows "New Password" and "Confirm New Password" fields. Any authenticated user who knows another evaluator's ValuatorID (which follows a pattern like K82XXXXXXX) could change that evaluator's password, locking them out or taking over their account.

This was partially reported by Nisarga as a "password-change flaw." Our bundle analysis confirms the exact mechanism: the API simply never asks for the current password.

Vulnerability 3: Evaluator Photos Served Without Authentication

The portal displays evaluator photographs via:

imageAsDataUrl = Pi_apiurl + "OnMarkWinWebAPI/face/GetUserPhoto/" + user_code + ".jpg"

This GET request is made through a plain http.get() call with no credentials, no auth headers, no tokens. Compare this to other API calls in the same bundle that include withCredentials: true:

// Authenticated API call (other endpoints):
httpClient.post(url, data, { withCredentials: true, headers: ... })

// Photo fetch (unauthenticated):
getImage(url) { return this.http.get(url, { responseType: "blob" }) }

If the server hosting /upload/ and /face/ doesn't enforce its own access control, anyone who guesses a user_code can view evaluator photographs — potentially including government-issued ID photos used for exam duty verification.

Why This Matters Beyond CBSE

The OnMark platform processes board examinations for dozens of Indian universities and state boards. Every vulnerability described above is a property of the shared codebase, not a CBSE-specific misconfiguration. If bcuosm.onmark.co.in is running the same build — and the identical IIS/ASP.NET headers and /cbseevalweb/ path strongly indicate it is — the same sequential PDF IDs, password-free change flow, and unauthenticated photo endpoints are likely exploitable there too.

The Coempt employees who pushed code to GitHub used the platform for at least three separate boards (CBSE, KNR, RTMNU), and the viswanthp/AP_SBTET_AUDIT repo reveals a fourth board (AP SBTET) running the same backend architecture with BillDesk payment integration, Razorpay IFS codes, and student photo uploads — all sharing the same weak HbCrypt hashing and SHA1 password storage.

Methodology

All findings are derived from:

  • A 1.7 MB Angular production bundle (main.js) recovered from the Wayback Machine, archived on 3 March 2026 from cbse.onmark.co.in
  • Coempt EduTeck's Selenium automation repositories on GitHub (segrgokul/New_Coempt_Automation, segrgokul/Ocr_To_Text_Automation, Sarthak-Sidhant/coempt)
  • SSL certificate transparency logs from crt.sh for *.onmark.co.in
  • Live HTTP header responses from active OnMark instances (May 2026)

No accounts were accessed. No APIs were called. No data was downloaded beyond static JavaScript bundles and public certificate records.
