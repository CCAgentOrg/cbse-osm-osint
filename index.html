Background

Following Nisarga Adhikary's disclosure of critical vulnerabilities in CBSE's On-Screen Marking (OSM) portal at cbse.onmark.co.in, and Sarthak Sidhant's investigation into CBSE's tender process favouring Coempt EduTeck, we conducted independent OSINT to map the full technical attack surface and supply-chain scope of this system.

This post covers findings not present in either previous disclosure: internal QA automation code, the complete board client list, full API endpoint inventory, and a forensic timeline showing the system was unstable during active evaluation.

OCR Integration Pipeline

The automation code reveals three distinct OCR methods used in the evaluation pipeline:

  1. Tesseract OCR (local) — for extracting text from scanned answer sheet images
  2. Google Gemini Vision API — AI-powered image analysis of handwritten responses, with evaluation prompt engineering
  3. Custom OCR extraction modules — structured data extraction from PDF answer sheets via dedicated Ocr_Text_Extract classes

The Gemini integration is notable: the automation code contains carefully crafted evaluation prompts that instruct the AI to assess handwritten answers against marking schemes. This is part of the automated quality assurance layer — not the primary marking system, but an AI review of evaluator consistency.

Why This Is a Disaster: Scriptable Portal + OTP Bypass

The Full Attack Chain — Proven by Coempt's Own Code

The leaked Selenium automation repo is not just a QA tool. It is a working proof-of-concept for a fully automated attack on the CBSE evaluation system. Here is how every piece fits together:

Step 1: Credentials from config.properties

The config.properties file parameterizes the entire attack. An attacker needs only change one value to target any board instance:

# Switch between boards with a single config change
login_name=osm                  # → targets https://cbse.onmark.co.in/cbseevalweb/
# login_name=sctevt_live_result # → targets https://sctevtexams.in/sn20Yz
# login_name=knr_live           # → targets https://knruhs.uonex.in/

URLs are resolved in BrowserManager.java via a urlBasedLogin() switch statement — every client instance has its entry. Portable by design.

Step 2: OTP Is Client-Side Only — No Server Validation

Look at the login flow in osm_Login_Page.java:

// 1. Fill credentials
sendKeys(OsmPom.getInstanceOsmLoginXP().userName, userName);
sendKeys(OsmPom.getInstanceOsmLoginXP().password, password);
sendKeys(OsmPom.getInstanceOsmLoginXP().schoolNo, schoolID);
sendKeys(OsmPom.getInstanceOsmLoginXP().dob, dob);

// 2. Click "Send OTP" button
click(OsmPom.getInstanceOsmLoginXP().sendOTP);

// 3. Wait for OTP to appear on page — as a visible input field
explicitWait(OsmPom.getInstanceOsmLoginXP().otpShown, 30);

// 4. If OTP is displayed, click Login — NO code reads or enters the OTP value
if(OsmPom.getInstanceOsmLoginXP().otpShown.isDisplayed()) {
    click(OsmPom.getInstanceOsmLoginXP().loginBtn);
    // Success alert: "You have successfully logged in the OSM portal"
}

The XPath locator for the OTP field confirms it's just a plain text input rendered client-side:

@FindBy(xpath = "//div/input[@class='form-input otp-input ng-untouched ng-pristine ng-valid']")
public WebElement otpShown;

The OTP is generated and displayed on the page itself — not sent via SMS, email, or any out-of-band channel. The Selenium code doesn't even need to read the OTP value. It simply waits for the element to appear, confirms it's visible, then clicks Login. This is a client-side-only pseudo-OTP that provides zero authentication security.

Step 3: Automated Canvas-Based Marking

Once authenticated, osmMainAssessmentPage.java automates the entire marking workflow:

// Navigate through every scanned answer sheet page
List<WebElement> scannedPages = driver.findElements(By.xpath("..."));
for (int pageNo = 1; pageNo <= scannedPages.size(); pageNo++) {
    page.click();  // Select answer sheet page

    // Interact with the marking canvas (HTML5 canvas element)
    WebElement canvas = driver.findElement(By.id("canvas" + (i+2)));
    new Actions(driver).contextClick(canvas).perform();  // Right-click

    // Select mark value from context menu
    List<WebElement> menuItems = driver.findElements(By.xpath("//div[contains(@class, 'context-menu')]//ul/li"));
    ((JavascriptExecutor) driver).executeScript("arguments[0].click();", target);

    // Simulate double-click to confirm mark allocation
    js.executeScript(leftDblClickScript, canvas, x, y);  // Coordinate-based dblclick
}

The marking interface uses HTML5 <canvas> elements with right-click context menus. The automation code programmatically clicks canvas elements at specific coordinates, selects mark values from context menus, and simulates double-clicks to confirm allocations — mimicking a human evaluator at machine speed.

Step 4: Scale with Jenkins CI

The test runner (osm_Exceution.java) is designed for Jenkins CI/CD execution:

@BeforeTest
@Parameters({"TestMethod"})
public void beforeTest(@Optional("") String testMethods) {
    methodsToRun = Arrays.asList(testMethods.split(","));
    // Running from Jenkins with TestMethod parameter
}

// Credentials fed via environment variables or Excel datasheets
String filePath = System.getenv("Filepath");
String loginName = System.getenv("Project_Login");
String browser = System.getenv("Browser");

This means the full attack — login, OTP bypass, marking, submission — can be triggered from Jenkins with parameterized credentials. Feed a spreadsheet of evaluator accounts, and one CI job can sequentially log in as each evaluator, auto-mark answer sheets, and submit — all unattended.

What We Found

Through passive OSINT — examining a 1.7 MB JavaScript bundle recovered from the Internet Archive's Wayback Machine, and cross-referencing it against Coempt's own Selenium automation code left on GitHub — we identified three high-confidence API-level vulnerabilities in the CBSE evaluation portal.

None of these were reported in the earlier responsible disclosure by security researcher Nisarga Adhikary, who focused on authentication bypass and route guard issues.

The API surface extracted from the archived Angular bundle reveals three additional vulnerabilities beyond what was previously disclosed. These are not CBSE-specific bugs — they are properties of the shared OnMark platform.

Vulnerability 1: Answer-Sheet PDFs Downloadable via Sequential IDs

The portal generates a total_marks_id for each evaluated answer sheet and serves the final marked PDF at a predictable URL:

apiurl + "Download/finalpdf/" + total_marks_id + ".pdf"

The bundle contains a hardcoded sample: total_marks_id: "93836". If this is an auto-incrementing database integer — which the five-digit number strongly suggests — any authenticated evaluator could enumerate IDs (93835, 93837, …) and download other evaluators' completed, annotated answer sheets. This is a textbook IDOR (Insecure Direct Object Reference).

The PDF opens in a new browser window at 800×600 with scrolling, meaning the system was designed for evaluators to review each other's marked scripts.

Vulnerability 2: Password Change Requires No Old Password

The ChangePassword endpoint accepts a payload of only two fields:

{ValuatorID: user_id, pin_NewPassword: new_password}

There is no old_password field — neither in the client-side form nor in the API payload. The HTML form only shows "New Password" and "Confirm New Password" fields. Any authenticated user who knows another evaluator's ValuatorID (which follows a pattern like K82XXXXXXX) could change that evaluator's password, locking them out or taking over their account.

This was partially reported by Nisarga as a "password-change flaw." Our bundle analysis confirms the exact mechanism: the API simply never asks for the current password.

Vulnerability 3: Evaluator Photos Served Without Authentication

The portal displays evaluator photographs via:

imageAsDataUrl = Pi_apiurl + "OnMarkWinWebAPI/face/GetUserPhoto/" + user_code + ".jpg"

This GET request is made through a plain http.get() call with no credentials, no auth headers, no tokens. Compare this to other API calls in the same bundle that include withCredentials: true:

// Authenticated API call (other endpoints):
httpClient.post(url, data, { withCredentials: true, headers: ... })

// Photo fetch (unauthenticated):
getImage(url) { return this.http.get(url, { responseType: "blob" }) }

If the server hosting /upload/ and /face/ doesn't enforce its own access control, anyone who guesses a user_code can view evaluator photographs — potentially including government-issued ID photos used for exam duty verification.

Why This Matters Beyond CBSE

The OnMark platform processes board examinations for dozens of Indian universities and state boards. Every vulnerability described above is a property of the shared codebase, not a CBSE-specific misconfiguration. If bcuosm.onmark.co.in is running the same build — and the identical IIS/ASP.NET headers and /cbseevalweb/ path strongly indicate it is — the same sequential PDF IDs, password-free change flow, and unauthenticated photo endpoints are likely exploitable there too.

The Coempt employees who pushed code to GitHub used the platform for at least three separate boards (CBSE, KNR, RTMNU), and the viswanthp/AP_SBTET_AUDIT repo reveals a fourth board (AP SBTET) running the same backend architecture with BillDesk payment integration, Razorpay IFS codes, and student photo uploads — all sharing the same weak HbCrypt hashing and SHA1 password storage.
