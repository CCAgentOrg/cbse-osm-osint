ni5arga Vulnerability Disclosures: CBSE OSM Portal

Researcher: nisarga (@ni5arga) | Blog: ni5arga.com | CERT-In Ref: CERTIn-16590126

This page documents all publicly disclosed vulnerabilities in CBSE’s On-Screen Marking (OSM) portal (built on Coempt EduTeck’s OnMark platform), as reported by security researcher nisarga between February–May 2026. All vulnerabilities were reported to CERT-In before public disclosure.

Vulnerability Catalog

VULN-01: Hardcoded Master Password in Frontend Bundle

Severity: 🔴 Critical Discovered: 25 Feb 2026 Status: Unpatched at time of disclosure (May 22)

A literal master password string was embedded in plain text in the Angular JavaScript bundle served at:

https://cbse.onmark.co.in/cbseevalweb/main.dc17c24606b3b008.js

When entered into the login form, the app automatically filled the OTP field and bypassed the entire authentication flow. No second factor required. Combined with publicly obtainable user IDs and school codes, this allowed login as any examiner.

Impact: Any attacker could authenticate as any examiner on the platform.

Source: Blog post — “Vulnerability 1” | X post

VULN-02: Client-Side OTP Validation (Security Theatre)

Severity: 🔴 Critical Discovered: 25 Feb 2026 Status: Unpatched at time of disclosure

The OTP step was entirely client-side. The server returned the OTP inside the authentication response, and JavaScript running in the browser compared the user’s input against it locally. Anyone inspecting network traffic could read the OTP directly.

Impact: Complete negation of the two-factor authentication mechanism.

Source: Blog post — “Vulnerability 2”

VULN-03: No Route Guards — Full App Walk-In

Severity: 🟠 High Discovered: 25 Feb 2026 Status: Unpatched at time of disclosure

The Angular SPA had zero canActivate route guards. Internal pages (/dashboard, /evalscriptsview, /heallscripts, /evaluatordetails, /verificationdashboard) were all directly navigable. Setting fake values in localStorage/sessionStorage was sufficient to reach any page without authentication.

localStorage.setItem('jwtToken', 'dev-token-12345');
sessionStorage.setItem('role_id', '23');
sessionStorage.setItem('eval', JSON.stringify({
  user_id: 'DEV001',
  role_id: '23',
  mobile_no: '9999999999',
  email: 'dev@dev.com',
  jwtToken: 'dev-token-12345'
}));
window.location.href = '/cbseevalweb/#/dashboard';

Impact: Unauthenticated access to all internal application pages.

Source: Blog post — “Vulnerability 3”

VULN-04: Password Reset Without Old Password Verification

Severity: 🔴 Critical Discovered: 25 Feb 2026 Status: Unpatched at time of disclosure

The ChangePassword API payload only contained ValuatorID and pin_NewPassword. The oldpassword field existed in the frontend component but was never sent to the server. Any ValuatorID could have its password reset without knowing the current one.

Impact: Combined with VULN-05, enables complete account takeover of any examiner.

Source: Blog post — “Vulnerability 4”

VULN-05: Systemic IDOR Across Entire API

Severity: 🔴 Critical Discovered: 25 Feb 2026 Status: Unpatched at time of disclosure

Almost every API call identified the acting user by reading ValuatorID/user_id from sessionStorage["eval"] — a client-side storage object editable via DevTools. The server trusted whatever ID the client sent instead of deriving it from the authenticated session. This is IDOR at the architectural level, not a single broken endpoint.

Attack chain: IDOR (act as any user) + VULN-04 (reset their password) = full account takeover → view answer scripts, alter marks.

Impact: Full account takeover of any examiner; ability to tamper with evaluation marks at national scale.

Source: Blog post — “Vulnerability 5”

VULN-06: SQL Injection

Severity: 🔴 Critical Discovered: ~25 May 2026 (reported 25 May) Status: Reported to CERT-In; no patch confirmation

A SQL injection vulnerability discovered in the OSM portal after the initial disclosure. Reported to CERT-In as a separate finding. Response: one-line acknowledgment email.

Impact: Potential database compromise, data exfiltration, or destruction of evaluation records.

Source: X post

VULN-07: CRUD + Shell Access on Production Servers

Severity: 🔴 Critical Discovered: 29 May 2026 Status: Disclosed publicly

Full create, read, update, delete (CRUD) access and shell access achieved on CBSE’s production servers — the same servers referenced in CBSE’s own circular.

Proof: Archive

Impact: Complete server compromise; ability to execute arbitrary commands, modify evaluation data, or deploy persistent backdoors.

Source: X post

Demonstration: Bad Apple video played on prod site

VULN-08: Super Admin Access on University OnMark Instance

Severity: 🔴 Critical Discovered: 29 May 2026 Status: Disclosed publicly

An integral OnMark subdomain was compromised to gain super admin access. The instance appeared to be used for evaluation of exams at various universities — extending the attack surface beyond CBSE to the entire OnMark platform ecosystem.

Impact: Super admin control of a separate OnMark deployment; potential cross-institution compromise.

Source: X post

VULN-09: AWS S3 Bucket Misconfiguration — Answer Sheets & Question Papers Exposed

Severity: 🔴 Critical Discovered: 30 May 2026 Status: Disclosed publicly

CBSE’s AWS S3 bucket was not configured properly. ListObjectsV2 worked without any authentication, and the bucket root was listable. This enabled pagination and enumeration of all media — including 2026 answer sheets and question papers. Multiple institutions were using the same bucket.

Impact: Anyone on the internet could download any scanned answer booklet across institutions. Massive PII exposure.

Source: X post

VULN-10: Shared Infrastructure Across OnMark Subdomains

Severity: 🟠 High Discovered: During investigation Status: Confirmed by independent researchers

Every CBSE-related subdomain under onmark.co.in (cbse1, cbse2, cbse3, cbse4, etc.) resolved to the same load balancer. Test environments shared infrastructure with production. The same hardcoded master password existed in the JS bundles across all subdomains.

Impact: A vulnerability in one instance compromises all instances. No meaningful environment separation between test and production.

Source: X post — subdomain resolution | X post — master password across domains

Key Takeaway

These are not sophisticated zero-days. They are architecture-level security failures — secrets in frontend code, client-side auth, no server-side authorization, shared infrastructure, unpatched software. The hardest part of exploiting them was reading a JavaScript file and editing a value in DevTools.

For a platform grading the futures of 17.8 lakh students, the basics are the least we should expect.
